Robotic Arm Simulator

A real-time digital twin of the SO-101 arm

We will build a real-time digital twin of the SO-101 robot arm: moving the physical leader arm by hand will move a rendered 3D arm live. We will implement the model loader, forward kinematics, and OpenGL renderer ourselves. As a stretch goal, a physics mode will track the measured angles using simulated joint torques.

02 / Problem Description

Low-cost arms are used to collect demonstrations for imitation learning. A live 3D twin would help us inspect poses, debug joint mappings, and record demonstrations with visual feedback. The challenge is to match the physical arm accurately while keeping input delay low and rendering at an interactive frame rate.

The SO-101 uses a leader/follower teleoperation setup. We will read its backdrivable leader as it is moved by hand, using six joint inputs: shoulder pan, shoulder lift, elbow flex, wrist flex, wrist roll, and gripper. A Python process will use LeRobot for readings and calibration, then send timestamped angles over a local socket to our C++ application for forward kinematics and OpenGL rendering.

Our main challenges are parsing URDF transforms and STL meshes, calibrating joint signs, offsets, and units, and keeping motor reads from blocking rendering. Shading, materials, and shadows must make the arm’s shape and pose clear without losing responsiveness.

03 / Goals and Deliverables

What we plan to deliver Baseline

  1. Live mirror mode. Render the arm at 60+ FPS with low input-to-display latency. Motor sampling and rendering will run independently; we will report their rates separately.
  2. Our own model loader and kinematics. Parse the SO-101’s URDF and STL meshes, then compute joint and link transforms without robotics libraries.
  3. Our own OpenGL renderer. Implement shading, materials, and shadow mapping on a ground plane, with a movable camera for inspecting poses.
  4. Record and replay. Save timestamped joint-angle sessions and replay them at their original timing for repeatable demonstrations and measurements.
  5. Measured performance. Report end-to-end latency in milliseconds, FPS, and simulated versus measured joint-angle error.

We will first complete one arm in mirror mode, using the SO-101 assets and a limited URDF feature set. Replay will support renderer work if hardware access is delayed. Physics work begins only after the baseline is complete.

What we hope to deliver Stretch

  1. Physics mode. Use measured angles as targets for a proportional-derivative (PD) controller that produces simulated torques. Implement Featherstone’s articulated-body algorithm (ABA), gravity, numerical integration, and joint limits ourselves.
  2. Ghost overlay. Show a transparent mirror-mode arm beside or over a solid physics arm, with plots of measured and simulated joint angles.
  3. Virtual contact and grasping. Add contact response and grasping of simple virtual objects if stable free-space dynamics is working.

Expected images and demo

Our demo will show a person moving the leader while the 3D arm follows, then replay the same recorded motion. We will include matched real/rendered poses, close-ups of materials and contact shadows on the ground plane, and performance plots. If physics works, we will show the ghost overlay during slow and fast motions, followed by a virtual grasp if implemented.

How we will measure quality

Latency
Film the physical arm and display together, count frames between matching motion events, and report median and 95th-percentile delay in ms, plus camera timing resolution. Internal timestamps will separate motor-read, processing, and rendering costs.
Frame rate
Target 60+ FPS during a repeatable session. Plot frame times and report median FPS and 95th-percentile frame time, with the laptop, resolution, and rendering settings.
Accuracy
Report per-joint mean absolute and maximum error in degrees between displayed state and timestamp-matched encoder readings. Since mirror mode copies input, also check physical joint angles at known poses and compare matched photos to catch calibration and transform errors.
Physics tracking
If implemented, measure per-joint tracking error and lag for slow sweeps and fast reversals. Report controller gains, timestep, and assumed masses and inertias.

Questions we plan to answer

How low can end-to-end latency go, and which stage limits it? How much do shadows and materials cost at 60 FPS? How closely does a simple dynamics model track the real arm, and where do calibration errors or model assumptions cause visible mismatch?

05 / Resources

  • LeRobot documentation and the SO-101 guide: motor access, setup, and calibration.
  • TheRobotStudio / SO-ARM100: SO-101 URDF and mesh assets. We will verify the model variant against our physical leader arm.
  • Roy Featherstone, Rigid Body Dynamics Algorithms, 2008: reference for our stretch dynamics implementation.

Platform: Python for LeRobot motor input and calibration; C++ for model loading, kinematics, OpenGL rendering, replay, metrics, and optional physics. We plan to use personal macOS laptops, GLFW for windows and input, GLAD for OpenGL function loading, and TinyXML2 for XML parsing. Our code will interpret the URDF and load STL geometry.

Hardware: We plan to use one physical SO-101 leader arm with its interface and power supply. We will confirm access before the November 13 start; recorded or synthetic joint sequences will support development if access is delayed.

Starting point and our contribution. We will use LeRobot only for motor readings and calibration, and reuse the robot’s URDF and mesh assets. We will build the loader, forward kinematics, OpenGL renderer, logging, replay, and metrics ourselves, plus physics if time permits. We will not use a robotics library for loading or kinematics, or an existing physics engine.

Existing team code: We plan to start a new codebase, using LeRobot and the robot assets as the external starting points.
